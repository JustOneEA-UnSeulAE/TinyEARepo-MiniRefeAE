P15: API-First ()
Principle 15: API-First Statement All system-to-system interactions are expected to be exposed and consumed via well-defined, standards-based APIs as the primary method of communication. Alternative integration approaches must be limited, justified, and governed. Rationale Direct backend integrations (such as shared databases or file transfers) tightly couple systems, creating brittle dependencies where changes in one system propagate to others, increasing maintenance costs and limiting future modernization. API-based system-to-system communication provides a consistent, standardized interaction model that enables systems to remain decoupled, modularized, reusable, and evolving independently, enforces mandatory GC security protocols, and reduces reliance on custom, point-to-point integrations. This aligns with the Government Canada’s Service and Digital Target - Enterprise Architecture (https://www.canada.ca/en/government/system/digital-government/policies-standards/service-digital-target-enterprise-architecture-white-paper.html), which promotes interoperability, reuse, and the reduction of data silos across government. Implications • Default API Integration: All BDM cross-system data exchange is expected to use published, standards-based APIs as the default approach, including GraphQL for data-querying operations, OpenAPI/REST for standard CRUD (create, read, update, delete) interactions, and AsyncAPI for event-driven patterns. • No Backdoor Access: Direct access to production databases, shared filesystems, shared memory, and ungoverned internal shortcuts are not permitted by default. • APIs as Products: APIs must be designed and managed as products, with clearly defined ownership, discoverability through an API catalog, well-documented contracts, service expectations (e.g., SLAs), and lifecycle management from publication to retirement. • Design for Public Consumption: APIs must be designed with the assumption that they will eventually be consumed by third parties or the Canadian public, even if currently only intended for internal use. • Internet-First Architecture: API communication must be designed with the assumption that it may occur over the public internet. Zero-Trust network design, including transport-layer encryption (HTTPS/TLS) and gateway-mediated authentication, must be baked in from the start, even within GC networks. • Platform and Vendor Neutrality: API implementations must remain technology-neutral, vendor-agnostic, and designed to abstract underlying systems, enabling portability across hybrid environments (on-prem, cloud, and SaaS). • Enterprise Pattern Alignment: API designs must align with Government of Canada Standards on APIs, enterprise integration patterns, including mandatory routing through secure API gateways and using shared data models, to ensure consistency and interoperability across systems. • Governance and Exceptions: Alternative integration approaches may be considered where API-based interaction is not feasible. Such cases must be formally documented, include a clear justification and transition roadmap where applicable, and be reviewed through the established architecture governance process.
